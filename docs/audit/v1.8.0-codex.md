- Important non-blocker:
  - `make release-check` は成功するが、期待バージョンを外から受け取らないため、今回のような `v1.8.0` 監査でも `VERSION=1.7.0` を正常扱いする。将来、`EXPECTED_VERSION=1.8.0 make release-check` のような検査を追加すると事故を減らせる。
  - `-Ss` の installed 判定は foreign package 一覧 (`pacman -Qm`) ベース、`-Si` の Installed は `pacman -Q <name>` ベース。通常の AUR 表示では問題になりにくいが、repo/AUR 同名や local package 状態を厳密に扱うなら表示ポリシー整理候補。
- Deferred / already tracked:
  - #96, #97, #98, #99: AUR build plan resolution cleanup は v1.9.0 予定のままでよい。
  - #134: `.SRCINFO` 優先の upgrade 更新判定と review 前 PKGBUILD 評価回避は v1.10.0 予定のままでよい。
  - #136: AUR RPC JSON parse failure handling は v1.10.0 予定のままでよい。
  - #123: build 後 make dependencies cleanup / `--rmdeps` 導線は v1.10.0 予定のままでよい。
  - #125: package size display は backlog / 検討棚のままでよい。
- Overall recommendation:
  - v1.8.0 scope の実装・UX・安全性については release 可。
  - tag / release 前に `VERSION` を `1.8.0` へ更新し、man page を再生成してから `make clean && make && make release-check` を再実行すること。

## 1. 不具合

### Findings

- `make clean`、`make`、`make release-check` は成功した。
- `make` は `src/jpacker.cpp` を C++20 / `-Wall -Wextra` で警告なしにビルドできた。
- `make release-check` は `VERSION=1.7.0` として成功した。これは整合性チェックとしては正しいが、v1.8.0 release 判断としては version bump 前であることを示す。
- `-Ss` / `-Si` の AUR status 表示は実測で期待通り。
  - `./jpacker -Ss 10moons-driver-t503`: `[orphaned]` を表示。
  - `./jpacker -Ss nkf`: `nkf` に `[installed]`、`thinkfan-git` に `[out-of-date]`、`thinkfinger` に `[orphaned]` を表示。
  - `./jpacker -Si 10moons-driver-t503`: `Maintainer: None`, `Installed: no`, `Orphaned: yes`, `Out of Date: no` を表示。
  - `./jpacker -Si thinkfan-git`: `Out of Date: yes` を表示。
  - `./jpacker -Si nkf`: `Installed: yes`, `Orphaned: no`, `Out of Date: no` を表示。
- repo package の `-Si` は pacman に委譲されることを確認した。
  - `./jpacker -Si pacman` は `Running: pacman '-Si' 'pacman'` の後、pacman の repo info を表示。
- `jpacker -Sc` 相当の routing は `sudo pacman` 経由になっている。
  - `src/jpacker.cpp:628-629` で `-Sc` を `sudo pacman <args>` へ委譲。
  - `src/jpacker.cpp:2701-2705` で `clean` operation も `sudo pacman '-Sc'` を先に実行。
  - 実際の `-Sc` 実行は pacman cache cleanup を伴うため、今回の監査では実行していない。
- pacman / makepkg への引数渡しは、少なくとも今回の scope では破綻を見つけていない。
  - pacman 引数は `join_shell_args()` / `shell_quote()` 経由 (`src/jpacker.cpp:802-812`, `954-971`)。
  - `--noconfirm` は pacman / makepkg execution にだけ足される (`src/jpacker.cpp:963-979`)。
  - `--rebuild` / `--cleanbuild` は makepkg 側だけに変換される。

### Release blocker candidates

- `VERSION` が `1.7.0` のまま。
  - `VERSION:1`
  - `./jpacker --version`: `jpacker v1.7.0`
  - `make` output: `Compiling src/jpacker.cpp (v1.7.0)`
  - `make release-check`: `VERSION=1.7.0` として成功
  - 判定: v1.8.0 tag / release 前の必須修正。実装 blocker ではないが、release artifact blocker。

### Non-blocker follow-ups

- `release-check` に期待バージョンを渡せるようにする。
  - 現状は repo 内の `VERSION` と binary / man / PKGBUILD の整合性だけを見るため、「今から v1.8.0 を出すつもりなのに 1.7.0 のまま」を検出できない。
  - Issue 化候補: release tooling / release-check enhancement。
- `-Ss` と `-Si` の installed 判定ポリシーを必要なら明文化する。
  - `-Ss`: `get_foreign_package_names()` により foreign package のみ `[installed]` (`src/jpacker.cpp:1569-1594`)。
  - `-Si`: `pacman -Q <Name>` により local installed state を見る (`src/jpacker.cpp:1629-1630`)。
  - 現時点では v1.8.0 blocker ではない。

## 3. セキュリティ脆弱性・安全性

### Findings

- root / sudo 実行の基本ガードは維持されている。
  - root 実行は help / version 以外で停止 (`src/jpacker.cpp:433-440`)。
  - pacman が必要な操作のみ `sudo pacman` を呼ぶ方針と一致。
- shell command construction は今回 scope の主要経路では quote / validation が入っている。
  - package name は `require_valid_package_name()` を通る。
  - AUR `PackageBase` も git URL 生成前に検証される (`src/jpacker.cpp:1557-1565`)。
  - shell 引数は `shell_quote()` / `join_shell_args()` 経由。
  - editor command は token を限定し、target path は quote される (`src/jpacker.cpp:852-873`, `982-985`)。
- AUR RPC URL は `curl_easy_escape()` を通して組み立てられている (`src/jpacker.cpp:1430-1436`, `1460-1465`, `1477-1495`)。
- `-Sc` 修正による新しい sudo risk は大きく見えない。
  - `-Sc` は pacman の標準 clean に委譲し、jpacker が root 権限で独自削除を始める形ではない。
  - jpacker cache の削除は通常ユーザー権限で、default no の prompt 後に行われる (`src/jpacker.cpp:2708-2724`)。
- review 前に PKGBUILD を評価しうる既存課題は残っている。
  - `upgrade` / source update の更新判定で `makepkg --printsrcinfo` を使う (`src/jpacker.cpp:2177-2181` と `is_update_needed()` 側)。
  - これは #134 として追跡済み。v1.8.0 の表示 cleanup / `-Sc` 修正による regression とは判断しない。
- AUR RPC JSON parse failure は一部で例外化しうる。
  - `AurClient::info()` / `info_many()` は `json::parse()` 例外を内部では握らない (`src/jpacker.cpp:1470`, `1498`)。
  - 呼び出し側で catch して failed にする箇所もあるが、扱いはまだ統一されていない。
  - #136 として追跡済み。今回の実測では AUR RPC は正常応答し、release blocker になる再現はなかった。

### Release blocker candidates

- 新規の明確な security blocker は見つからなかった。
- #134 は設計上重要だが既知の v1.10.0 項目であり、今回の v1.8.0 scope による新規 regression とは見ていない。
- #136 も重要だが、現時点の通常 AUR response で release を止める再現はない。

### Non-blocker follow-ups

- cache cleanup の hardening。
  - `XDG_CACHE_HOME` 由来の cache path を使うため、将来は cache directory の所有者 / symlink / canonical path を確認してから `remove_all` する方がより安心。
  - 現状は通常ユーザー権限かつ default no prompt 付きなので v1.8.0 blocker ではない。
- `sudo rm -f` を使う source-build preference 削除系は package name validation と shell quoting で守られているが、将来は `sudo install` / `sudo rm` の外部 command surface を整理してもよい。
