## Codex audit との差分・追加指摘

差分監査として、Codex が明示していなかった点を以下に挙げる。いずれも release blocker ではない。

1. **#136 のカバー範囲が `search_names_by_provides()` を含むべき（追加指摘）**
   - Codex は JSON parse 例外の未保護箇所として `AurClient::info()` (`src/jpacker.cpp:1470`) と `info_many()` (`:1498`) を挙げた。
   - これに加え、`AurClient::search_names_by_provides()` の `json::parse(response)` (`:1450`) も未保護である。
   - さらにこの関数は `find_aur_provider()` (`:1521`) の **try ブロックの外** で呼ばれており、壊れた JSON を受け取ると例外がそのまま上位へ伝播する。最終的には呼び出し経路上位（`cmd_deps` 等）の try-catch で「その target が失敗」になるためクラッシュはしないが、Codex が挙げた 2 箇所とは「catch 位置の遠さ」という性質が異なる。
   - 事実: クラッシュ再現は未確認（通常の AUR 応答では発生しない）。#136 のスコープ記述にこの箇所を 1 つ足すと取りこぼしが減る。

2. **`-Sc` と `clean` の差がユーザー向け文書に出ていない（追加指摘）**
   - 実装上、`jpacker -Sc` は `sudo pacman -Sc` へ委譲するのみで jpacker cache はクリーンしない (`src/jpacker.cpp:629`)。`jpacker clean` は `sudo pacman -Sc` の後に jpacker cache cleanup を行う (`:2701-2725`)。
   - help には `clean`（"Clean package/build caches"）はあるが `-Sc` の独立行はなく、man も `clean` の項に `sudo pacman -Sc` を実行する旨があるだけで、`-Sc` 単体と `clean` の差は明示されていない。
   - 推測: pacman 互換オプションを全て help に列挙しない方針からは妥当な省略だが、`-Sc` だけは v1.8.0 で routing を変えた経緯があるため、1 行の補足があるとユーザーの誤解（`jpacker -Sc` で jpacker cache も消えると思う）を防げる。

3. **README の EDITOR 表現が config の EDITOR を織り込んでいない（軽微）**
   - 実際の優先順位は「環境変数 `EDITOR` > `jpacker.conf` の `EDITOR` > `nano`」で、`build_from_git()` (`:2186-2187`) と `cmd_edit_src()` (`:2557-2558`) で一致しており整合している。
   - man (`man/jpacker.8.in:111-112`) と config example は「環境変数 EDITOR が優先」を正しく説明している。
   - 一方 README の `Preferred editor (default: $EDITOR or nano)` は config の `EDITOR` を経路から落とした表現。破綻ではないが、man / config example とのニュアンス差。non-blocker。

## 1. 不具合

- 新規の機能不具合は見つからなかった。
- 軽微な観察（不具合ではない）:
  - `search_aur()` は `parse_aur_package_info()` で `info` を作った後、Description だけ raw json から再取得している (`src/jpacker.cpp:1596-1597`)。`info.Description` を使えば一貫するが、実害はない。
  - `-Ss` の終了コードは `pacman_ret == 0 || aur_found` で 0 を返す (`:626`)。pacman 検索が空でも AUR がヒットすれば成功扱い。意図通りで問題なし。

## 2. 意図しない挙動・UXに反する挙動

- `-Ss` の status tag 表示順は COMPATIBILITY.md と一致（`[installed]` → `[out-of-date]` → `[orphaned]`、cyan / red / yellow） (`src/jpacker.cpp:1586-1594`、`docs/COMPATIBILITY.md:84-94`)。不一致なし。
- `-Si` の AUR info は `Maintainer` / `Installed` / `Orphaned` / `Out of Date` を表示 (`:1654-1657`)。v1.8.0 スコープの表示要件 (`docs/COMPATIBILITY.md:96-101`) を満たす。
- `-Ss` の `[installed]` は foreign package 一覧 (`pacman -Qm`) ベース (`:1571`)、`-Si` の `Installed` は `pacman -Q <name>` ベース (`:1116-1119`、`:1655`)。
  - `-Si` で AUR info を出すのは「repo に存在しない package」のみ (`cmd_sync_info` の `is_repo_package` 分岐、`:2390`) のため、実用上 foreign に限られ、両者の差が表面化する場面は限定的。Codex の non-blocker 判断に同意。
- `-Qua` の出力は `name old -> new` のみで out-of-date / orphaned tag は出さない (`:2476-2478`)。更新チェック用途として妥当で、`-Ss` / `-Si` との不自然な不一致ではない。
- EDITOR の優先順位は `build_from_git` と `cmd_edit_src` で一致しており、help / man / config example の説明と大枠で整合（README の表現のみ上記 3 の通り軽微な差）。
- 上記「差分・追加指摘 2」の `-Sc` / `clean` の差は UX 上の小さな分かりにくさだが、blocker ではない。

## 3. セキュリティ脆弱性・安全性

- root / sudo ガード維持 (`:433-441`)。pacman が要る操作のみ `sudo pacman` を呼ぶ方針と一致。
- shell command 構築は `shell_quote()` / `join_shell_args()` 経由で quote され (`:802-812`, `:954-961`)、package name は `require_valid_package_name()` を通る。AUR RPC URL は `curl_easy_escape()` で escape される (`:1432-1435`, `:1462-1465`, `:1485-1491`)。
- editor command は `is_safe_command_token()` で token を限定し (`:852-858`)、対象 path は quote される。`cmd_edit_src` の temp file は `mkstemp` + `require_valid_package_name` で安全 (`:2562-2566`)。install 失敗時のみ temp を残すのは意図的。
- `-Sc` 修正による新規 sudo risk は大きくない（pacman 標準 clean への委譲、jpacker cache 削除は通常ユーザー権限 + default no prompt） (`:2708-2724`)。Codex に同意。
- **#136 関連（上記差分・追加指摘 1）**: `search_names_by_provides()` の `json::parse` が未保護かつ `find_aur_provider` の try 外。壊れた AUR 応答で例外伝播するが上位 try-catch で target 失敗に収束。クラッシュ再現は未確認、通常応答では発生しない。non-blocker。
- **#134 関連**: `is_update_needed()` が `makepkg --printsrcinfo` を実行し (`:1085`)、これは PKGBUILD を bash 評価しうる。フロー上 `upgrade` 経路で「reset --hard で最新 PKGBUILD 取得 → printsrcinfo（評価）→ Edit PKGBUILD? prompt」の順のため、レビュー prompt の前に評価が走る。ただしこれは v1.8.0 以前からの Smart Upgrade 既存挙動であり、v1.8.0 スコープ（表示 cleanup / `-Sc` routing）の新規 regression ではない。#134 として追跡済み。deferred 同意。
- cache cleanup hardening（`XDG_CACHE_HOME` 由来 path の owner / symlink / canonical path 確認）は Codex 指摘通り non-blocker。
